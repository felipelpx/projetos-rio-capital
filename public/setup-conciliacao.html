↔ Setup — Conciliação entre previsões e faturas

O mesmo custo pode entrar no ERP por dois caminhos: como previsão (um pagamento manual ou uma despesa recorrente) e, mais tarde, como fatura no Contas a Pagar. Se os dois ficarem de pé, o mês conta o custo a dobrar.

A partir do v127, ao gravar uma fatura nova o ERP procura previsões parecidas e pergunta se é o mesmo custo. Ao ligar, a ocorrência prevista sai do Fluxo Futuro — só aquela. Numa previsão de 4 parcelas sai a parcela ligada e as outras três ficam; numa avença mensal sai o mês ligado e a avença continua nos seguintes.

1Abre o SQL Editor do Supabase

Vai a Supabase SQL Editor e cola o SQL abaixo.

2Corre o SQL

-- Na fatura fica o rasto de que previsão substituiu
alter table faturas add column if not exists previsao_origem text;   -- 'manual' | 'recorrente'
alter table faturas add column if not exists previsao_id     text;   -- id do pagamento_extra ou da regra
alter table faturas add column if not exists previsao_data   date;   -- a ocorrência concreta

-- A ocorrência prevista que já tem fatura. Guarda-se a OCORRÊNCIA, não a
-- previsão inteira: a parcela 2/4 sai, as outras três ficam.
create table if not exists previsoes_baixas (
  id              text primary key,
  origem          text        not null,      -- 'manual' | 'recorrente'
  origem_id       text        not null,      -- id do pagamento_extra ou da regra recorrente
  data_ocorrencia date        not null,      -- a data da ocorrência consumida
  fatura_id       text,
  empresa         text,
  valor_previsto  numeric,
  valor_fatura    numeric,
  criado_por      uuid,
  created_at      timestamptz not null default now()
);

-- Uma ocorrência só pode ser consumida uma vez (é isto que o upsert usa)
create unique index if not exists idx_baixas_ocorrencia
  on previsoes_baixas(origem, origem_id, data_ocorrencia);
create index if not exists idx_baixas_fatura on previsoes_baixas(fatura_id);

alter table previsoes_baixas enable row level security;

drop policy if exists "ler baixas"    on previsoes_baixas;
drop policy if exists "criar baixas"  on previsoes_baixas;
drop policy if exists "editar baixas" on previsoes_baixas;
drop policy if exists "apagar baixas" on previsoes_baixas;

create policy "ler baixas"    on previsoes_baixas for select using (true);
create policy "criar baixas"  on previsoes_baixas for insert with check (true);
create policy "editar baixas" on previsoes_baixas for update using (true) with check (true);
create policy "apagar baixas" on previsoes_baixas for delete using (true);

-- Um item de mapa que entrou sem fatura (uma avença, uma previsão) pode
-- recebê-la mais tarde: é aqui que fica essa ligação.
alter table mapas_pagamento_itens add column if not exists fatura_id text;

-- Tempo real: a previsão desaparece do fluxo sem ser preciso recarregar
do $$ begin
  if not exists (select 1 from pg_publication_tables
                 where pubname = 'supabase_realtime' and tablename = 'previsoes_baixas') then
    alter publication supabase_realtime add table previsoes_baixas;
  end if;
end $$;

notify pgrst, 'reload schema';

3Confirma

No ERP: Contas a Pagar → + Nova fatura. Lança uma fatura com o valor e a data de uma despesa recorrente que exista (ex.: a contabilidade deste mês). Ao carregar em Guardar abre o painel “Este custo já estava previsto”.

Depois de ligar: a fatura fica com a etiqueta verde ↔ previsão e, no Fluxo Futuro, esse mês da despesa deixa de ter a linha prevista — passa a ter só a fatura.

4Mapas de pagamento (v130)

No Pagamentos → Novo mapa (e no + Adicionar pagamentos de um mapa por aprovar) aparecem agora as despesas recorrentes sem fatura, marcadas como Recorrente, com a data em que se pagam. Uma ocorrência por mês: novembro e dezembro da mesma avença são duas linhas.

Dentro do mapa, um item que entrou sem fatura mostra o botão 🔗 ligar fatura. Ao ligar, a ocorrência prevista sai do Fluxo Futuro — é a mesma baixa do passo 2, por isso este SQL serve os dois.

Enquanto não correres o SQL

A fatura é criada na mesma, mas a previsão não sai do fluxo e o ERP avisa-te com uma mensagem a dizer exactamente isso. Não se perde nada; fica é o custo a contar duas vezes até correres o SQL.

Desfazer: eliminar a fatura devolve a previsão ao Fluxo Futuro automaticamente. O custo continua a existir — só deixa de ter fatura.
